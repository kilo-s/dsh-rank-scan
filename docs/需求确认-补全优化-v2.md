# 需求确认 · 补全优化 ①书页缓存扩全站 + ③补全移出阻塞路径（v2）

- 日期：2026-10-17
- 来源：使用者「扫描一次太久、榜单还补不全」+ 实测复盘（抓 19 榜只花 71s，补全却花 ~5 分钟 / 91 请求）
- 状态：**已确认，实现中**（本文件是实现硬规范）

## 1. 实测基线（做这件事的依据）
- 2026-10-17 00:24 手动扫描：抓榜 finishedAt 00:25:40（**71 秒**），其后补全又跑了约 **5 分钟 / 91 请求**（1 请求/秒）。
- 当天 371 行 / **366 个唯一书号**；其中 **323 个在昨天也出现过**（88%）⇒ 有书页缓存时每天只需真打 **~43 本**。
- 同一次扫描内跨榜重复只有 5 个书号 ⇒ 站内去重几乎无收益，**收益全在跨天复用**。
- 现状：书页缓存只有起点（`qidian-cache.ts`，7 天 TTL）；刺猬猫/菠萝包/番茄每天全量重打。

## 2. 决定（Q1–Q6）

| # | 决定 | 说明 |
|---|---|---|
| Q1 | 新增**通用书页缓存** `scan/book-cache.ts` | 键 `site:bookId`，值 = 书页能给的字段（collect/words/title/author/score/readCount）+ `fetchedAt`；TTL 默认 7 天（`bookCacheTtlDays` 可配）。**只缓存真拿到值的字段，缺失一律 null、不补 0**；一条都没取到就不写缓存（下次重试）。 |
| Q2 | 刺猬猫 / 菠萝包 / 番茄的补全都走这个缓存 | 逐行先查缓存：命中即用（0 请求），未命中才请求并回写。**起点的 `qidian-cache.ts` 保持不动**（避免动到已验收的起点通道）。 |
| Q3 | 番茄补全同时覆盖书名/作者 | 现有 `enrichFanqieTitles` 只写书名；本次让它把 author/wordNumber 也写进缓存（换一天标题缺字时**可从缓存直接修好，0 请求**）。 |
| Q4 | 补全**移出扫描的阻塞路径** | `/scan` 抓完榜即落盘并返回（**约 71 秒**）；补全改为**后台补全工人**（3 秒后起跑，逐榜跑，受请求预算与每榜每日 3 次上限）。进度写 state（`enrichRun`）并可由 `/timer` 读到。 |
| Q5 | 面板要能看出「在补全」 | 榜单页/概览显示「补全中 N/M 榜」；扫描结束后自动刷新一次，让补上的字段出现。 |
| Q6 | 顺手查 ④（批量接口） | 只做取证与结论，不改实现；探不到批量接口就如实写结论。 |

## 3. 明确不做
- 不改抓榜部分的并发/限速（**限速 1s/请求不可协商**，spec-扫榜插件-v1:87）。
- 不改五态判定、变化集、列口径。
- 不动 `qidian-cache.ts` 的数据格式（已验收）。
- ④ 不引入任何新请求通道；只是探测报告。

## 4. 验收口径
- 单测：新的通用缓存命中/过期/只写有值条目；`enrichBookPages` 命中缓存时**请求数为 0**；补全编排函数在「全部命中缓存」时不再请求。
- 离线闸门（acceptance -SkipLive）全绿；`scripts/test-local.ps1` 全绿。
- 真机验证：手动扫描后 `/scan` **立即返回**（不再等补全），进度可见；再跑一次同样扫描时补全请求数应显著下降（缓存命中）。

### 已知边界（不是缺陷）
- 起点图三江的补全受「站点时刻」门槛约束（12:40 之后才动它，避免在别站时刻打它）⇒ 凌晨手动扫描后它会留在待办里，12:40 的 tick 续跑时补齐。
- 每榜每日最多 3 次尝试；用尽仍缺 ⇒ 面板显示「当日已试 N 次」。
- 首轮扫描仍会真打书页（缓存是空的时候），收益从**第二次**开始显现。
