# 需求确认 · 补全持久化 + 显示口径修复（v1）

- 日期：2026-10-16
- 来源：使用者「面板榜单显示问题」6 条反馈 + 根因复盘（补全落盘早于补全、无持久状态）
- 状态：**已确认，实现中**（本文件是实现硬规范；改动只能以「完善方案」提出再裁决）

## 1. 术语
- **补全（enrich）**：抓完榜页后再逐本进书页取站上不给的字段（起点/起点图=收藏·字数；刺猬猫/菠萝包=字数·收藏·书名·作者；番茄=干净书名·作者·字数）。
- **裸行**：某榜快照里 rows 存在、但补全字段为 null 的行。
- **补全未完成**：该榜该数据日的快照里仍有可补的裸行（或本榜补全过程被取消/超时打断）。
- **数据日期**：本地自然日；补齐永远只针对**最近一个数据日**。

## 2. 已确认的决定（Q1–Q7）

| # | 决定 | 说明 |
|---|---|---|
| Q1 | 补全必须**持久化** | 补全状态写进 state（`enrichPending`/`enrichTried`），带**数据日期**；跨插件重载/DSH 重启后按 tick 续跑，直到补齐或当日放弃。 |
| Q2 | 补全不得无限重跑 | 每榜每日最多尝试 3 次，每次调用受**请求预算**（起点/起点图 40、刺猬猫/菠萝包 24）限制；跨日自动清理。 |
| Q3 | 不再重抓榜页 | 补全续跑**只跑补全**（本地快照 → enrichBoard），不重抓榜页 ⇒ 与「每榜每日 1 次」纪律不冲突。 |
| Q4 | 补全未完成必须**可见可修** | 面板：榜单页显示「补全未完成 · 缺 N 条」+ 一键「补齐本榜」；宿主 /board 下发 `enrich: {pending, missing, reason, tried}`。 |
| Q5 | 番茄「在读变化」= 我方按天的**在读差** | 与 spec-扫榜插件-v1 及取证文档一致（站方 rankPosDiff 是名次升降，另有一套）。对外字段 `extra.valueDelta`；客户端读它、绝不回退到名次差；`row.delta` 只放名次差。 |
| Q6 | 起点图首订锚 **n-1** | 锚点 = 请求日 − 1 天（站点口径：上架 24h 后才结算，站点自身默认 n-1）。**只有 n-1 页面没有数据行时才回退 n-2**（最多再退 1 天，照搬三江「空期回退」写法）；「有行但首订全空」如实保留 —— 那是该日期还没结算完的正常状态，回退会把名单换成更早的一天、反而失真（实现时对此做了修正）。首订行 `extra.showDate` = 实际页面日期；面板标注源数据日期。 |
| Q7 | 缺失一律 null | 不补 0；回退/放弃都要如实记 warning，不静默。 |

## 3. 明确不做
- 不改「变化」列的既有语义（`row.delta` = 名次差，值型榜也保留该列）。
- 不做启动即全量补全（只跑 pending；避免每次重启打站点）。
- 不改 usesRankDelta / 跨期保护 / 列集合口径。
- 不引入运行时依赖；lib/ 不入库。

## 6. 实现后的口径修正（2026-10-16，随证据改，非擅自改需求）
- **首订回退判据**：Q6 原写「n-1 无数据或首订全空时回退」，实现时发现「有行但首订全空」是**常态**
  （站点当天页就是这样，首订要等结算），按原写法会把名单静默换成 n-2 而丢掉「还没结算」这个事实。
  改为「**只有页面无数据行才回退**」，并在行上/说明里如实标出「首订尚未结算」。
- **起点续跑走缓存通道**：起点榜的补全续跑从「适配器内置 enrich（无缓存、整榜重打）」改成
  **书页缓存通道**（qidianEnrichBoard），续跑只打没缓存/缓存过期的书。
